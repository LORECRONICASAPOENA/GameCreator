# PROMPT DE IMPLEMENTAÇÃO — APOENA AGAR GAME CREATOR v3.5

## Gerador de Itens MOBA + Editor Visual de Loja + Integração ao Banco Central

### 1. OBJETIVO PRINCIPAL

Quero ampliar o meu programa existente, **Apoena Agar Game Creator v3.5**, adicionando um sistema completo de criação de equipamentos MOBA e um editor visual das interfaces da loja que serão utilizadas pelos jogadores dentro do jogo Apoena Agar, desenvolvido em Godot 4.

**Não quero criar outro aplicativo. Não quero substituir o Creator. Quero integrar as novas funcionalidades ao sistema que já existe.**

O Creator funciona offline, utiliza uma interface HTML aberta pelo navegador e já possui ferramentas de criação, gerenciamento de imagens, itens, inventário, menus, poções, cards e exportação para Godot 4.

A implementação precisa preservar todas essas funções e os dados já cadastrados.

A interface deverá seguir uma filosofia **mobile-first**, funcionando no PC e no Android, com rolagem vertical, controles simples, botões visuais e ferramentas que não exijam programação manual do usuário.

Existem dois públicos diferentes:

- **Desenvolvedor:** usa o Creator para criar itens, editar layouts, arrastar elementos, configurar atributos, gerenciar a biblioteca e exportar o resultado.
- **Jogador:** usa somente a loja final dentro do jogo. Não tem acesso aos controles de edição, coordenadas, ferramentas de programação ou propriedades internas.

Essa separação é obrigatória.

### 5. LAYOUT DO GERADOR DE ITENS

O formulário principal deve seguir exatamente esta ordem visual:

**1. Imagem do equipamento**

Um quadrado grande, com possibilidade de:

- Arrastar imagem do PC para o programa.
- Selecionar arquivo manualmente.
- Escolher imagem da biblioteca.
- Importar várias imagens.
- Ajustar enquadramento.
- Visualizar transparência.
- Substituir imagem.
- Exportar ícone.

Aceitar PNG, JPG e WebP. Preservar o arquivo original e preparar uma versão otimizada para a loja.

**2. Nome do item**

Campo de texto simples.

**3. Destino**

Selecionar MOBA, Exploração ou Ambos, conforme compatibilidade.

**4. Categoria**

Arma, armadura, escudo, artefato mágico, acessório, movimento, suporte ou consumível.

**5. Subcategoria**

Exemplos: espada, machado, arco, manopla, escudo, bota, cristal, anel e poção.

**6. Atributos**

Controles numéricos para ATK, DEF, HP, AUR, velocidade, poder de habilidades, crítico, regeneração e outros atributos registrados.

Permitir vários atributos no mesmo equipamento.

**7. Efeitos**

Escolher efeitos ativos ou passivos predefinidos, com parâmetros editáveis.

**8. Economia**

Preço de compra, valor de revenda, requisitos e componentes necessários.

**9. Evolução**

Selecionar equipamentos necessários para fabricar versões superiores.

**10. Prévia**

Mostrar o equipamento exatamente como aparecerá na loja.

**11. Salvamento**

Salvar rascunho, publicar na biblioteca, duplicar ou exportar.

O formulário deve oferecer configurações automáticas sugeridas, mas permitir modificações manuais.

### 7. DUAS TELAS DE LOJA

**A. Loja de início de partida**

- Disponível na fase inicial, antes da liberação de movimento.

As duas telas poderão compartilhar o mesmo estilo e os mesmos componentes, mas deverão permitir ajustes de layout independentes.

### 10. SISTEMA DE EFEITOS SEM PROGRAMAR

O desenvolvedor não deverá precisar digitar código para criar um item comum.

Construir uma biblioteca de comportamentos predefinidos, por exemplo:

- Aumentar ataque
- Aumentar defesa
- Aumentar vida
- Aumentar Aurium
- Aumentar velocidade
- Recuperar HP
- Recuperar AUR
- Aplicar escudo temporário
- Aplicar efeito de lentidão
- Reduzir tempo de recarga
- Conceder regeneração
- Melhorar curas
- Conceder resistência temporária

Cada comportamento terá parâmetros editáveis por controles visuais.

Exemplo:

**Efeito:** Aumentar ataque\
**Valor:** 3\
**Duração:** Enquanto equipado\
**Acúmulo:** Conforme regra definida

O sistema não deverá gerar código arbitrário para cada novo item.

Os comportamentos precisam existir e ser testados no runtime do jogo. Se um efeito ainda não for suportado, o Creator deverá marcá-lo como pendente, em vez de simular que ele já funciona.

**Importante:** no Apoena Agar existem poderes que causam dano proporcional ao HP do alvo. O balanceamento não deve presumir que todo bônus de ATK aumenta automaticamente o dano de qualquer habilidade. Cada habilidade precisa respeitar sua fórmula registrada.
